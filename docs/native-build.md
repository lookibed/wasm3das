# Native tiers: AOT, standalone context, JIT, and the measurements

The port is Daslang source in every tier; nothing was rewritten in C++. What
differs is how it executes. This document replaces the working notes
`native_aot_status.md`, `native_aot_fastcall_2026-09-08.md`,
`release_squeeze_plan_2026-09-10.md` and `benchmark_2026-09-07.md`; the
authoritative current measurement is `tests/manual/fixture_report.md`
(generated by `tests/manual/run_fixtures.py`).

## 2. AOT lowering findings (all fixed in `.das`, never in generated C++)

Each is a Daslang construct whose AOT lowering differs from its interpreter
lowering; none is a fidelity bug.

1. **An enum of another module is declared only where a value is used.**
   `m3_types.das` names no `M3ValueType` value, so `M3TaggedValue._type` used
   an undeclared enum. Fix: `m3_TaggedValueNone()` in `m3_types.das`, which
   spells out the zero-initialised `M3TaggedValue` C describes.
2. **`array<void const?>` has no instantiated builtins** (`TArray<void const *>`
   does not link). Fix: `array<void?>` in `m3_Call` (`m3_env.das`) and
   `repl_invoke` (`app/wasm3.das`); the deviation from `const void *
   i_argptrs[]` is documented at `m3_Call`.
3. **`reinterpret<pointer>(function value)` yields the address of the value.**
   `das_cast<TT*>::cast(const QQ &)` returns `&expr`, so a `Func` written into
   a code page became a pointer into the current stack frame (ASan:
   `stack-use-after-return`; every raw import jumped through a dangling frame).
   Every write of a function value into a code page goes through `u64`:
   `reinterpret<void?>(reinterpret<u64>(f))`, correct in both backends. The
   three sites: `EmitWord` (`m3_code.das`, the whole opcode table),
   `FindAndLinkFunction` (`m3_bind.das`, the `M3RawCall` for
   `op_CallRawFunction`) and `op_Compile` (`m3_exec.das`, `rewrite[0] =
   unsafe(reinterpret<code_t>(reinterpret<u64>(@@op_Call)))`). Upstream PR
   #3974 fixes `das_cast` itself; once the pin carries it the hops are
   unnecessary but harmless.
4. No stack knob was needed: `options stack = 67_108_864` and `ulimit -s
   262144` carried over unchanged, `assert_exhaustion` still traps.

The dispatch sentinel `m3Ret_nextOp` must be `var` for the same family of
reasons (`docs/execution-design.md`).

## 3. The `aot` tier's AOT link miss (item A4, open)

`tmp/native/bin/wasm3das -aot-strict` reports `error[50101]: AOT link failed on
@m3_exec::op_Return` (and `op_i32_Equal_rs`). Cause: `Function::aotHash`
includes `flags.fastCall`, a whole-program property (a one-expression body
whose address is taken nowhere). The AOT tool compiles each module as its own
root, where `@@op_Return` (taken in `m3_compile.das` for the operation table)
is invisible, so the AOT side hashes `fastCall = true`; the runtime compiles
the whole program, clears it and finds no entry. 51 functions of `m3_exec` are
`fastCall` on the AOT side; `op_Return` is the only one whose address another
module takes. Rejected after measurement: the fold of the `let` string global,
branch elimination order, `[inline]`, every CodeOfPolicies difference, file
paths. Side finding: `op_Return` and `op_End` (identical bodies) register under
the same semantic hash; harmless, worth mentioning upstream. Reproducer for an
upstream issue: a module whose `op_ok` reduces to `return <const>`, a root that
takes `@@op_ok` and dispatches through a table, a strict host; `options
no_fast_call = true` in the module links everything.

Port-side workaround, not applied yet: after `op_Return` in `m3_exec.das`

```das
let private c_aot_op_Return_ref : IM3Operation = @@op_Return
```

so both compilations agree; `options no_fast_call` is program-wide and strips
`fastCall` from about 50 interpreter functions, not recommended. Cost of the
miss: `fib 30` 0.300 -> 0.281 s, `fib 35` 3.25 -> 3.04 s (3.6–6 %), nothing
measurable elsewhere. `build_port.sh` should run the finished binary once with
`-aot-strict` and fail on `50101`; today a binary with unlinked bodies ships
silently.

## 4. Standalone context (`ctx`)

`scripts/build_port.sh ctx` -> `tmp/native-ctx/bin/wasm3das`, launcher
`scripts/wasm3-ctx`. The pinned daslang carries the `-ctx` fixes (upstream
#3967, PR #3838: emission of a required module's initialized global, the
`InitGlobalVar` link signature, `[init]` run order). Limitation on the pin:
`[init]` functions of required modules cannot run in a standalone context, so
`m3_compile::init_compile_operation_tables` is an explicit, idempotent call
from `m3_NewEnvironment`; a new required-module `[init]` fails the `-ctx`
build with `error[50503]` naming it. Upstream `7a9ae1077` (after the pin, "a
required module's [init] runs from the generated constructor") lifts that;
the explicit call stays because it is harmless on both.

The emitter after the pin generates a C API instead of the C++ class
`das::wasm3::Standalone`: `wasm3_create()` runs the global initializers and
the `[init]` functions, `wasm3_main(ctx)` is the exported `main`,
`wasm3_last_error(ctx)` carries an exception text instead of a C++ throw,
`wasm3_destroy(ctx)` frees the instance, `wasm3_shutdown_runtime()` drains
the process. `native/standalone_main.cpp` uses that API (2026-09-20); a host
written against the old class does not compile on the current daslang.

The binary runs `main` on a thread with an explicit 256 MiB stack
(`pthread_attr_setstacksize`, `CreateThread dwStackSize`), so the bare release
asset traps `[trap] stack overflow` under the default 8 MiB shell limit (spec
17863/17863, WASI 12/12 without any launcher).

The host also owns two start-up details (E5, section 7). Under glibc it
sets `M_ARENA_MAX` to one arena and a 64 MiB `M_TOP_PAD` before the thread
starts, because the program thread's own malloc arena grew page group by
page group: 3108 `mprotect` calls per start (`strace -c`), now 9. And it
leaves through `_exit` with the streams flushed instead of tearing the
context and the module registry down (about 3 ms of a 15 ms start, memory
the process returns anyway); `WASM3DAS_TEARDOWN=1` runs the full teardown,
which the ASan and leak-check builds need.

The emitter itself runs from an overlay of DASLANG_ROOT (`tmp/dasroot-ctx`)
that carries the emitter patches of section 7 the checkout lacks, one
marker string per patch (`build_port.sh`, the `ctx` arm); the checkout is
never written and `WASM3DAS_CTX_EMITTER=stock` builds without the patches.

Link flags (B1–B3, measured 2026-09-10, gcc 11.4, one build per row, aot_ctx
total of the 98-check fixture run, mean of four; C wasm3 stayed at 3.02–3.09 s):

| variant | flags | unstripped | stripped | total | start |

| base | as shipped before | 52.83 MB | 37.54 MB | 7.41 s | 29 ms |

Run-to-run spread is ±0.1 s, so only the combined set's 0.35 s and 4 ms of
start are outside the noise; execution proper is flat, the win is image size
and relocation. `-fno-strict-aliasing` is what daScript compiles its own
sources with under gcc (`CMakeCommon.txt`, "GNU uses strict aliasing
optimizations too hard"). LTO buys nothing (two translation units, and the
daslang archives are not built with IPO). The compiler archive cannot be
dropped by a link flag: without `liblibDaScript.a` the link fails only on
`register_Module_Ast`, which the emitted module table lists although nothing in
the port requires `ast`; an empty stub gives 37.7 MB / 26.4 MB stripped and
still passes the spec suite (item B9). The link flags above are what a
scratch build must repeat when the context is emitted by hand (section 7,
E1): the emission `daslang -dasroot <root> utils/aot/main.das -- -ctx
app/wasm3.das <out>/ctx`, then the compile of `native/standalone_main.cpp`
(`-I<out>/ctx`) and of `<out>/ctx/wasm3.das.cpp` with the flag set of
`build_port.sh ctx`, then the link against `liblibDaScript.a`,
`liblibDaScript_runtime.a`, `liblibUriParser.a`, `-lpthread -ldl -lm`.

The C++ compiler is not a lever either. `build_port.sh` takes `clang++` when
it exists and `g++` otherwise; on the stand only `clang++-18` is installed,
so the shipped ctx and aot binaries are gcc 11.4 builds, whereas c2das
compiles its AOT objects with `clang++-18`. Measured 2026-09-21, the same
emitted context built both ways, two interleaved fixture runs each
(`--runtimes wasm3,aot_ctx`, execution without start): gcc 11.4 4.15 s and
4.26 s, clang++-18 4.42 s and 4.49 s, the binaries 45.7 MB and 45.4 MB. gcc
stays the default. The gap to C wasm3 (1.7x on the corpus, 4x on fib) is
the program, not the build: every threaded-interpreter hop is an indirect
call through the code page that no compiler inlines, the five interpreter
registers travel by reference, and C wasm3 tail-jumps between operations
where the port returns to `RunLoop`. c2das gets 0.97–1.24x of `clang -O2` on
the same daslang because its translated decoders are straight-line code
with no dispatch loop to pay for.

## 5. JIT

`WASM3DAS_JIT=1` appends `-jit` to the daslang command line, `WASM3DAS_JIT_OPTS`
further switches (`--jit-opt-level` 0..3, default 3), `WASM3DAS_APP` another
entry point. The DLL cache lives in `.jitted_scripts/<namespace>/<content
hash>.dll` relative to the working directory (gitignored), keyed by function
set, opt level, size level, prologue, debug-info and target; stale artifacts
are garbage-collected on the next run. The JIT writes its `[I] LLVM JIT: ...`
progress to stdout, so the WASI driver needs a wrapper that strips those
lines. `-jit` stays opt-in and off the gate.

History, all closed by the pin (`docs/upstream-status.md`): a module-qualified
`math::` intrinsic segfaulted codegen (#3968), `reinterpret<u64>(@@fn)` emitted
an invalid aggregate bitcast (#3969), the interpreter yielded 0 for the same
cast in store contexts (#3970), and a `let` sentinel lost its identity across
the JIT boundary (the `var m3Ret_nextOp` change). Still open: #3991, `const`
pointer parameters emitted `readonly`, wrong results at `--jit-opt-level >= 1`;
the port declares every parameter the callee writes through as `var` (which
is what C declares), so it is correct at O3: spec 17863/17863, WASI 12/12,
fixtures 86/86 on master `388691eb1`. JIT start is 3.5 s of codegen cold,
0.15 s from the DLL cache (0.55 s per process warm). The fixture harness
records `--jit-opt-level=3` in its report header; O0 is the control when a JIT
column disagrees with the baseline.

Both JIT tiers get their own operation dispatch, generated by an infer pass
under `prog.policies.jit_enabled` alone, because an invoke through a function
value is never a tail call in LLVM: `docs/execution-design.md` section 7 for
the mechanism and the `options _m3_dispatch` shapes, section 6 E9 below for the
objdump evidence and the numbers, section 7 E9 for the verdict. Every other
tier compiles `m3_exec.das` as written, in C's form.

objdump of the branch point's own cached JIT DLL says what the shapes are
worth. The operation already tail-jumps — `op_SetRegister_i32` is six
instructions ending in `jmp nextOpImpl` — but `nextOpImpl` itself is 156 bytes:
`push %rbx`, `sub $0x50,%rsp`, the five interpreter registers written into an
argument buffer on the stack (`mov %rax,(%rsp)`, `%rsi,0x10(%rsp)`,
`%rdx,0x20(%rsp)`, `%rcx,0x30(%rsp)`, `vmovq %xmm0,0x40(%rsp)`), a null test,
`mov 0x30(%rdi),%rax` to load `SimFunction::jitFunction`, `call *%rax`, then
`add $0x50,%rsp; pop %rbx; ret`. That is the generic wrapper ABI of E7 (c): a
call and a return, 0x58 bytes of stack, per executed wasm operation.

objdump of the generated DLL, all three shapes: an operation is six
instructions ending in `jmp m3_DispatchOp` (`op_SetRegister_i32`: `mov
(%rdi),%eax; add $0x8,%rdi; shl $0x2,%eax; cltq; movslq (%rsi,%rax,1),%rcx; jmp
…`), `nextOpImpl` is a single five-byte `jmp` into the dispatch, and the
dispatch's arms are `jmp`s back into the operations — no frame anywhere in the
chain. What differs is the dispatch's own prologue and size:

| shape | `m3_DispatchOp` size | entry to first branch | inner shape | exe `.text` |
|---|---:|---:|---|---:|
| `"tree"` | 0x3e3a | 91 bytes (6 pushes, a frame, 4 SSE constants, 2 globals) | 276 `jmp`s, no indirect | 416 758 |
| `"chain"` | 0x2f0a | 79 bytes, same hoisting | 7 indirect `jmp *` (jump tables) | 412 038 |
| `"noinline"` | 0x19d8 | **11 bytes** (`mov (%rdi),%eax; add $0x8,%rdi; cmp`) | 250 `jmp`s, no indirect | 382 998 |

The fat prologue of `"tree"` and `"chain"` is LLVM inlining the small
operations into the dispatch and hoisting their constant loads to its entry,
where every dispatched operation pays for them; `[hint(noinline)]` removes it
entirely. That it still does not win says the prologue is not the dominant
term — the comparisons are — which is why `"chain"`, whose jump table is one
indirect jump instead of nine compares, is the default.

### E10, what an operation costs under the JIT against gcc (2026-09-22, `perf/jit-op-cost`)

E9 left the exe tier at about 2x the ctx tier on execution with the dispatch
already reduced to a jump table, so the remaining gap had to be in the
per-operation code. objdump of the same operation in both binaries — the `t`
implementation symbol of the cached JIT DLL against the `W` symbol of
`tmp/native-ctx/bin/wasm3das` — says where, counted on the hot path (entry to
the tail jump; the ctx bodies carry a long cold tail of daslang's `das_invoke`
and `throw_error_at` paths that never runs):

| operation | ctx hot path | exe hot path, E9 | what the LLVM version does on top |
|---|---:|---:|---|
| `op_i32_Add_ss` | 21 | 11 + dispatch | — the body itself is *smaller*: no frame, no null test, `shl`+`cltq` where gcc uses `movslq`+scaled index |
| `op_i32_Add_rs` | 18 | 7 + dispatch | — |
| `op_SetSlot_i32` | 17 | 6 + dispatch | — |
| `op_SetRegister_i32` | (inlined away) | 6 + dispatch | — |
| `op_i32_LessThan_sr` | 19 | 9 + dispatch | — |
| `op_BranchIf_r` | 18 | 6 + dispatch | — |
| `op_i32_Load_i32_r` | 8 | **40** | 4 pushes + `sub $0x18`, the five registers spilled, `call *(%r9)` into the runtime's `memcpy`, then `call m3_DispatchOp; ret` — the chain stops being a chain |
| `op_Call` | 43 | 52 | `call jit_str_cmp@plt` for `r == m3Err_none` (gcc: `strcmp@plt`, both paid) |
| `op_Entry` | 17 | 54 | the same string comparison, plus `memset8`/`memcpy` calls C also makes |
| `op_Loop` | 59 | 25 | — |
| `op_Return`, `op_ContinueLoop` | 2 | 2 | — |
| `Call` (the helper) | 15 | 5 | — |
| the dispatch step | 12 (load the word, 2 null tests, `jmp *%r9`) | 8 (`mov`, `add`, `cmp`, table, `jmp *`) | but +16 prologue / +8 epilogue for every operation LLVM did not inline into `m3_DispatchOp` |

So the arithmetic and slot operations are already better than gcc's and the
dispatch step is cheaper; the gap is three things, two of which the port owns:

1. **Every load and store was a runtime call.** C writes the access as a
   constant-size `memcpy` and says why ("memcpy here is to support non-aligned
   access on some platforms"). gcc folds it; the LLVM JIT keeps daslang's
   `memcpy` as a call through the runtime's function pointer, which needs a
   frame, spills the five interpreter registers, and — because the call is not
   last — turns the operation's tail jump into `call m3_DispatchOp; ret`, one
   native frame per executed load. Written as the typed access it means, 40
   instructions become 11 and the tail jump is back. Coremark minimum of four
   interleaved rounds: 16.98 s → 13.43 s.
2. **`r == m3Err_none` is a string comparison.** C tests a pointer against
   NULL; the port's `M3Result` is a string and `m3Err_none` is `""`, so both
   backends call out — `strcmp@plt` in ctx, `jit_str_cmp@plt` in the JIT — on
   the return path of every wasm call, host call and trapping division. `empty`
   (AGENTS.md's spelling for C's `== NULL`) is still a call in the JIT, but the
   cheap one: fib 35 median 0.92 s → 0.80 s.
3. **What is left is daslang's.** `empty(string)` and the other builtins are
   invoked through the runtime's function-pointer table instead of being
   intrinsified, and an invoke through a function value is still never a tail
   call (E7 (c)). Both are named in section 8.

`"chain_noinline"` — the jump table plus `[hint(noinline)]`, the fourth shape,
added because E9 had the two properties tied together — was measured and
rejected. It does exactly what objdump predicts (the dispatch drops to 0xad8
bytes, 8 instructions from entry to the indirect jump, no push, no frame, and
the arms become single five-byte `jmp`s), and it still loses: fib 35 median
0.92 s against 0.78 s for `"chain"`, coremark minimum 14.13 s against 13.43 s.
The prologue is paid only by the operations LLVM did *not* inline, and taking
the inlining away costs the hot ones two jumps each. The shape stays available.

## 7. The plan to beat C wasm3, and the experiments so far (2026-09-21)

returns to `RunLoop` and passes the five interpreter registers through
memory, where C wasm3 tail-jumps with the registers in machine registers. The
compilers are not the lever (section 4, gcc against clang), and neither is
PGO (below). Three experiments, run in sequence on a quiet stand, each on
the same emitted program and the same 98-check corpus:
